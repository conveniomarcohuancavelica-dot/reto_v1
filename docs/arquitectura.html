API Gateway + Microservicios + OAuth 2.0

Documentación de arquitectura para el reto técnico: registro y consulta de pedidos a través de un API Gateway único, con dos microservicios independientes, autenticación JWT y trazabilidad end-to-end.

Java 17 Spring Boot 3.3 WebFlux Spring Cloud Gateway JWT · HS256 MySQL 8 Docker Compose

API Gateway

Único punto público. Valida JWT, enruta por path y propaga X-Trace-Id. Sin lógica de negocio ni composición de respuestas (no es un BFF).

Order Service

Dueño de pedidos, estados e historial. Llama a Inventory Service vía WebClient (HTTP reactivo, no bloqueante).

Inventory Service

Dueño de productos, stock y disponibilidad. Persistencia independiente, sin conocer a Order Service.

Auth Service

Emisor de JWT (HS256). Reemplaza a un Identity Provider externo tipo Keycloak, manteniendo el mismo estándar OAuth2/JWT.

02 Decisiones técnicas

Justificación breve de cada decisión, lista para defender en la revisión técnica.

Auth Service propio (no Keycloak)

Mismo estándar OAuth2/JWT, pero con control total del ciclo de vida del token: emisión, claims, expiración y validación, sin depender de un componente externo adicional para el alcance de este reto.

MySQL, una base por microservicio

Motor relacional estable con integridad transaccional, adecuado para persistir pedidos, historial e inventario. Cada microservicio es dueño exclusivo de su esquema — orderdb y inventorydb nunca se comparten.

WebClient reactivo en vez de RestTemplate

El reto pide explícitamente comunicación síncrona vía HTTP reactivo. WebClient es no bloqueante y es el cliente estándar en un stack WebFlux.

JPA (bloqueante) envuelto en Mono.fromCallable + boundedElastic

R2DBC para MySQL no tiene el mismo nivel de madurez que JPA. Las operaciones de persistencia bloqueantes se ejecutan en un scheduler dedicado (Schedulers.boundedElastic()) para no bloquear el event loop de Netty.

Fuera de alcance a propósito: Saga Orchestrator, Kafka, Outbox, Event Sourcing, CQRS, Kubernetes y Dispatch Service. El flujo es síncrono y de bajo acoplamiento distribuido — Order Service solo depende de Inventory Service en el instante de crear el pedido, así que no se requiere consistencia eventual entre servicios.

03 Estados del pedido

Las transiciones válidas están centralizadas en el enum OrderStatus (principio de responsabilidad única) — no hay "ifs" de reglas de negocio esparcidos por el código.

PENDING ──→ CONFIRMED ──→ CANCELLED
PENDING ──→ FAILED ──→ sin stock (opcional, estado terminal)
  • PENDING — recién creado, aún no confirmado.
  • CONFIRMED — hay stock, se confirmó y se reservó.
  • CANCELLED — cancelado desde PENDING o CONFIRMED únicamente.
  • FAILED — no se pudo confirmar por falta de stock.

Cualquier transición fuera de este grafo (ej. cancelar un pedido ya CANCELLED) se rechaza con 409 INVALID_TRANSITION, evitando cancelaciones duplicadas.

04 Flujo de creación de un pedido

1. POST /api/v1/orders           → se persiste en PENDING
2. Order Service consulta stock  → GET /api/v1/inventory/availability (WebClient)
3a. Hay stock                   → se reserva stock → estado CONFIRMED
3b. No hay stock                → error controlado → estado FAILED
4. Cada transición                → se registra en order_history con su X-Trace-Id

07 Trazabilidad · X-Trace-Id

  • El Gateway genera un X-Trace-Id si el cliente no lo envía, o respeta el recibido.
  • Se propaga como header hacia Order Service e Inventory Service en cada llamada saliente.
  • Se agrega al MDC de Logback → aparece en cada línea de log de los tres servicios.
  • Se incluye en toda respuesta, tanto de éxito como de error.

08 Seguridad

El Gateway valida el JWT como Resource Server antes de enrutar. Order Service e Inventory Service vuelven a validar el mismo token de forma independiente (defensa en profundidad): cada servicio es seguro por sí mismo y testeable en aislamiento, sin depender ciegamente de la red interna.

Los tres validan con la misma clave secreta (HS256) que usa Auth Service para firmar, vía NimbusReactiveJwtDecoder.withSecretKey(...).

10 Testing

JUnit 5 + Mockito + StepVerifier (Reactor Test) en Order Service e Inventory Service. Casos cubiertos: creación con stock suficiente/insuficiente, transición inválida (doble cancelación), pedido inexistente y reserva de stock.

cd order-service && mvn test
cd inventory-service && mvn test

API Gateway + Microservicios + OAuth 2.0

Documentación de arquitectura para el reto técnico: registro y consulta de pedidos a través de un API Gateway único, con dos microservicios independientes, autenticación JWT y trazabilidad end-to-end.

Java 17 Spring Boot 3.3 WebFlux Spring Cloud Gateway JWT · HS256 MySQL 8 Docker Compose

API Gateway

Único punto público. Valida JWT, enruta por path y propaga X-Trace-Id. Sin lógica de negocio ni composición de respuestas (no es un BFF).

Order Service

Dueño de pedidos, estados e historial. Llama a Inventory Service vía WebClient (HTTP reactivo, no bloqueante).

Inventory Service

Dueño de productos, stock y disponibilidad. Persistencia independiente, sin conocer a Order Service.

Auth Service

Emisor de JWT (HS256). Reemplaza a un Identity Provider externo tipo Keycloak, manteniendo el mismo estándar OAuth2/JWT.

02 Decisiones técnicas

Justificación breve de cada decisión, lista para defender en la revisión técnica.

Auth Service propio (no Keycloak)

Mismo estándar OAuth2/JWT, pero con control total del ciclo de vida del token: emisión, claims, expiración y validación, sin depender de un componente externo adicional para el alcance de este reto.

MySQL, una base por microservicio

Motor relacional estable con integridad transaccional, adecuado para persistir pedidos, historial e inventario. Cada microservicio es dueño exclusivo de su esquema — orderdb y inventorydb nunca se comparten.

WebClient reactivo en vez de RestTemplate

El reto pide explícitamente comunicación síncrona vía HTTP reactivo. WebClient es no bloqueante y es el cliente estándar en un stack WebFlux.

JPA (bloqueante) envuelto en Mono.fromCallable + boundedElastic

R2DBC para MySQL no tiene el mismo nivel de madurez que JPA. Las operaciones de persistencia bloqueantes se ejecutan en un scheduler dedicado (Schedulers.boundedElastic()) para no bloquear el event loop de Netty.

Fuera de alcance a propósito: Saga Orchestrator, Kafka, Outbox, Event Sourcing, CQRS, Kubernetes y Dispatch Service. El flujo es síncrono y de bajo acoplamiento distribuido — Order Service solo depende de Inventory Service en el instante de crear el pedido, así que no se requiere consistencia eventual entre servicios.

03 Estados del pedido

Las transiciones válidas están centralizadas en el enum OrderStatus (principio de responsabilidad única) — no hay "ifs" de reglas de negocio esparcidos por el código.

PENDING ──→ CONFIRMED ──→ CANCELLED
PENDING ──→ FAILED ──→ sin stock (opcional, estado terminal)
  • PENDING — recién creado, aún no confirmado.
  • CONFIRMED — hay stock, se confirmó y se reservó.
  • CANCELLED — cancelado desde PENDING o CONFIRMED únicamente.
  • FAILED — no se pudo confirmar por falta de stock.

Cualquier transición fuera de este grafo (ej. cancelar un pedido ya CANCELLED) se rechaza con 409 INVALID_TRANSITION, evitando cancelaciones duplicadas.

04 Flujo de creación de un pedido

1. POST /api/v1/orders           → se persiste en PENDING
2. Order Service consulta stock  → GET /api/v1/inventory/availability (WebClient)
3a. Hay stock                   → se reserva stock → estado CONFIRMED
3b. No hay stock                → error controlado → estado FAILED
4. Cada transición                → se registra en order_history con su X-Trace-Id

07 Trazabilidad · X-Trace-Id

  • El Gateway genera un X-Trace-Id si el cliente no lo envía, o respeta el recibido.
  • Se propaga como header hacia Order Service e Inventory Service en cada llamada saliente.
  • Se agrega al MDC de Logback → aparece en cada línea de log de los tres servicios.
  • Se incluye en toda respuesta, tanto de éxito como de error.

08 Seguridad

El Gateway valida el JWT como Resource Server antes de enrutar. Order Service e Inventory Service vuelven a validar el mismo token de forma independiente (defensa en profundidad): cada servicio es seguro por sí mismo y testeable en aislamiento, sin depender ciegamente de la red interna.

Los tres validan con la misma clave secreta (HS256) que usa Auth Service para firmar, vía NimbusReactiveJwtDecoder.withSecretKey(...).

11 Auditoría y correcciones · 12 ago 2026

Revisión completa de funcionalidad, uso de Lombok, dependencias no usadas y dockerización. Se verificó cada endpoint de la colección Postman contra el código, y se compiló cada archivo con javac real para descartar errores de sintaxis.

Nota de proceso: una revisión anterior había reportado varios de estos mismos hallazgos y dijo haberlos corregido, pero los cambios nunca quedaron guardados en el proyecto entregado. Esta auditoría partió de cero y verificó cada corrección directamente en el código antes de darla por hecha.
1 MapStruct declarado pero nunca usado Limpieza

Dependencia + annotationProcessorPath en order-service e inventory-service. El mapeo real siempre se hizo a mano con toResponse() — ningún archivo tenía @Mapper.

Corrección Se quitó la dependencia y el processor de ambos pom.xml.
2 @Transactional inefectivo por auto-invocación Bug

En OrderServiceImpl, saveHistory() era un método protected anotado con @Transactional pero invocado como this.saveHistory(...) desde dentro de la misma clase. Spring AOP solo intercepta llamadas que pasan por el proxy — la auto-invocación nunca lo hace, así que la anotación no protegía nada.

Antes Guardado del pedido y del historial sin atomicidad real entre ambos. Corrección Se extrajo a un bean nuevo, OrderTransitionWriter, inyectado normalmente — la llamada externa sí pasa por el proxy y ambos guardados quedan atómicos.
3 @Transactional inefectivo en WebFlux + JPA bloqueante Bug

InventoryServiceImpl.reserveStock() envolvía Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic()) dentro de un método @Transactional. El método devuelve el Mono al instante (sin bloquear), así que Spring abre y cierra la transacción de forma síncrona antes de que el trabajo real se ejecute — en otro hilo, más tarde. La transacción quedaba vacía.

Corrección Se quitó la anotación. La atomicidad real la sigue dando el único repository.save() (transaccional por sí mismo en Spring Data JPA) combinado con bloqueo optimista vía @Version.
4 Actuator ausente pese a estar referenciado Bug

SecurityConfig permitía /actuator/health/** y application.yml tenía el bloque management, pero faltaba la dependencia spring-boot-starter-actuator en los tres servicios — el endpoint no existía en runtime.

Corrección Dependencia agregada en auth-service, order-service e inventory-service.
5 Healthchecks y arranque de Docker Compose Hardening

Ninguno de los 4 servicios Java tenía healthcheck, así que depends_on solo esperaba a que el contenedor arrancara (service_started), no a que Spring terminara de inicializar — puede tardar 15–30s con Hibernate DDL y Spring Cloud Gateway.

Corrección healthcheck vía /actuator/health en los 4 servicios y condition: service_healthy en toda la cadena: mysql → inventory-service → order-service → api-gateway.
6 Puerto MySQL en riesgo de choque Hardening

mysql-order exponía el 3306 del host — el puerto por defecto de casi cualquier instalación local de MySQL/XAMPP/WAMP.

Corrección Movido a 3316 (y 3317 para mysql-inventory). Los fallbacks en application.yml para correr fuera de Docker también se actualizaron.
7 Fuga de MDC en el API Gateway Bug

TraceIdGlobalFilter ponía el traceId en el MDC con doOnEach(...) pero nunca lo limpiaba. En el pool de hilos compartido de Netty (event loop), esto puede filtrar el traceId de una petición hacia los logs de otra petición concurrente que reutilice el mismo hilo.

Corrección Alineado al patrón que ya usaban order-service/inventory-service: doFirst(() → MDC.put(...)) + doFinally(() → MDC.remove(...)).
8 Columna id con tipo inconsistente (BINARY vs texto) Bug

Los campos @Id private UUID id; con GenerationType.UUID mapean por defecto a BINARY(16) en Hibernate 6 + MySQL. Pero data.sql de inventory-service inserta con la función UUID() de MySQL, que devuelve un string de 36 caracteres — al chocar con una columna BINARY(16) el valor se trunca/corrompe. ddl-auto: update tampoco puede corregir el tipo de una columna ya creada en un volumen de Docker existente, por eso parecía necesario un ALTER TABLE ... MODIFY COLUMN id VARCHAR(36) manual.

Corrección Se fuerza hibernate.type.preferred_uuid_jdbc_type: CHAR en order-service e inventory-service, para que todos los UUID mapeen a CHAR(36) de forma consistente con lo que data.sql inserta. Importante Esto NO corrige una columna ya creada con el tipo viejo en un volumen existente — hay que recrearlo: docker compose down -v && docker compose up --build.
9 Lombok limitado a lo estándar Hardening

Las entidades ya usaban solo @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder — nunca @Data, @Value, @EqualsAndHashCode ni @ToString, que son las anotaciones que suelen chocar con JPA (recursión en relaciones, o romper el contrato de equals con proxies de Hibernate).

Corrección Se agregó lombok.config en la raíz del proyecto fijando esa disciplina para los 4 servicios (accessors estilo JavaBean, advertencia si alguien agrega @Data/@Value más adelante).

Verificado y sin cambios (no eran bugs)

  • Entidades JPA usan @Getter @Setter @Builder de Lombok — nunca @Data, que sería riesgoso en entidades por el equals/hashCode/toString autogenerado.
  • DTOs son record de Java, no Lombok — práctica moderna correcta.
  • Colección Postman verificada endpoint por endpoint contra controllers, DTOs y SecurityConfig: sin inconsistencias de campos, rutas ni headers.
Verificación de sintaxis: los 53 archivos .java compilan sin errores reales con javac 21 (el entorno de auditoría no tiene acceso a repo.maven.apache.org, así que no reemplaza un mvn test real — se recomienda correr docker compose up --build para la validación final).
